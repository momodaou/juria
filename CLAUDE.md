# JURIA — Contexte du projet

## Description
JURIA est une application de gestion de cabinet d'avocats développée pour **JFC Avocats Mali** (droit OHADA). Elle couvre l'ensemble du cycle de vie du cabinet : dossiers, clients/KYC, procédure et échéances, facturation, gestion administrative/RH, et un assistant IA d'aide à la rédaction.
Dépôt GitHub : https://github.com/momodaou/juria.git

Spécification initiale : démo interactive HTML (`JURIA demo - MAJ 09.08.2026.html`) fournie par l'utilisateur, retranscrite dans `DOC/JURIA - Dossier de Specifications Fonctionnelles - MAJ 16.08.2026.docx`.

### Périmètre fonctionnel (17 modules)
1. **Cockpit** — vue d'ensemble et pilotage du cabinet (KPIs, délais critiques, rentabilité, tâches perso)
2. **Dossiers 360** — liste des dossiers + fiche 360° (parties, délais, pièces, temps, communications, instances)
3. **Nouveau dossier (ouverture)** — contrôle des conflits d'intérêts puis création (référence, lettre de mission, KYC, tâches auto)
4. **Clients & KYC** — registre clients, suivi KYC/LBC-FT, registre des originaux physiques confiés
5. **Échéancier** — délais de procédure par dossier + échéances administratives récurrentes (fiscal, social, ordinal)
6. **Rôle d'audience** — agenda hebdomadaire des audiences, diffusion équipe, planning des diligences, retours d'audience
7. **Registre du courrier** — enregistrement arrivée/départ, référencement auto, GED, déclenchement d'événements
8. **Atelier d'actes** — génération d'actes via modèle GED ou draft IA, visas à jour, en-tête cabinet
9. **Bibliothèque** — jurisprudence, textes OHADA, veille législative, modèles, consultations, checklists
10. **Plan d'action** — suivi des tâches du cabinet en kanban (à faire/en cours/à valider/terminé)
11. **Chrono & Facturation** — édition auto de factures/notes de frais, TVA selon localisation client, multi-devises, suivi des impayés
12. **Dépenses & caisse** — charges du cabinet, débours clients refacturables, petite caisse, vignettes de plaidoirie
13. **Rétrocessions** — calcul et suivi des rétrocessions d'honoraires (Associé 30% / Collab. avocat-stagiaire-Of Counsel 25% / Collab. non-avocat 10%, "tout ou rien" après encaissement intégral), suivi Pro Bono
14. **Accès & permissions** — matrice d'accès (Collaborateur / Associé-Partner / Finance-Direction), délégations temporaires, journal d'audit
15. **Cabinet (RH)** — équipe et charge de travail, congés, alertes RH, pointage, compteur d'heures, option paie légère
16. **Assistant IA** — capacités d'assistance (résumé, extraction de faits, chronologie, analyse contractuelle, traduction, comparaison) — phase à valider
17. **Portail client** — extranet client (dossiers, factures, messagerie) — phase 4

### Acteurs / rôles
**11 statuts réels** (précisés par l'utilisateur le 17/08/2026, remplacent l'estimation initiale à 8) : Avocat associé, Avocat Of Counsel, Avocat collaborateur, Avocat stagiaire, Collaborateur non-avocat/juriste, Administrateur général, Assistante juridique et administrative, Comptable, Assistant comptable, Administrateur IT, Archiviste — plus Client (via portail, sans authentification séparée, cf. limitation documentée du module Portail client). Mapping technique et système de permissions : voir « Statuts du personnel + permissions configurables » dans l'État actuel ci-dessous.

### Règles métier transverses clés
- Export Excel/CSV + impression PDF (en-tête cabinet) sur chaque écran
- Alertes par délai : J-7 rouge / J-15 orange / au-delà bleu
- Gestion multi-instance (1re instance / appel / cassation-CCJA) sous référence de dossier unique
- FCFA devise pivot, EUR à taux fixe (655,957), autres devises au taux du jour verrouillé à l'émission
- Échéances fiscales/sociales maliennes pré-paramétrées (TVA, INPS, ITS, IS, patente, Ordre des avocats, RC pro)

## Stack technique (réelle, adoptée le 16/08/2026)

> ⚠️ Cette stack remplace une proposition initiale (Next.js/TypeScript + Prisma) écartée après découverte d'un kit de démarrage déjà préparé par l'utilisateur (`JURIA kit demarrage - MAJ 09.08.2026.zip`), utilisé comme base réelle du projet. Voir `HISTORY.md` (entrée du 16/08/2026, "Pivot stack technique").

### Frontend
- **Angular 22** (standalone components, signals, `@if`/`@for`), TypeScript
- Projet complet dans `APP/frontend/` (scaffoldé via `@angular/cli@22`)

### Backend
- **API Node.js/Express** (JavaScript, pas TypeScript), dans `APP/backend/`
- Auth par JWT (`jsonwebtoken` + `bcryptjs`), pas de framework auth tiers
- Upload fichiers : `multer` ; stockage GED : `@google-cloud/storage`

### Base de données
- **PostgreSQL 15**, schéma SQL géré à la main (`APP/db/schema.sql`, pas d'ORM/Prisma) — 36+ tables (dossiers, clients, facturation, rétrocessions, échéances, RH, etc.)
- Client : `pg` (requêtes SQL directes, pas de query builder)

### Déploiement — Google Cloud Platform
- **Compute** : Cloud Run (conteneur API Node.js)
- **Base** : Cloud SQL for PostgreSQL
- **Stockage** : Google Cloud Storage (GED)
- **Secrets** : Secret Manager
- Script de référence : `JURIA deploiement gcp - MAJ 01.08.2026.sh` (dans les Documentations utilisateur, à intégrer dans le dépôt)
- Domaine cible : `extranet.jfcavocats-mali.com`

### IA
- Assistant IA prévu via Gemini/Vertex AI (`IA_MODEL=gemini-1.5-flash` dans `.env.example`) — `backend/src/ia.js`

### Développement local
- **Docker** pour tout (Node.js n'est pas installé sur la machine de dev actuelle) : `docker compose up --build` (API + Postgres), front lancé via conteneur `node:22` (voir `APP/README.md`)

Trois états dérivés côté UI : `actif=TRUE` → Actif ; `actif=FALSE ET valide_le IS NULL` → en attente de validation ; `actif=FALSE ET valide_le IS NOT NULL` → suspendu.

Écran `Mon compte` (`pages/mon-compte/`) accessible depuis le menu par tous.

Réutilise le même générateur que la création de compte. - ⚠️ Motif récurrent de bug rencontré : dans ce codebase (SQL brut, pas d'ORM), `COALESCE($n, 'litteral')` ou `CASE WHEN $n = 'litteral' THEN…` sur une colonne de type ENUM **ou UUID** Postgres provoque une erreur de typage dès que le paramètre est réutilisé dans un contexte non typé. Toujours caster explicitement (`$n::mon_enum`, `$n::uuid`) ou dupliquer le paramètre. Autre variante rencontrée : un placeholder `$n` numéroté mais jamais réellement utilisé dans le texte SQL (reliquat de refactoring) fait échouer `could not determine data type of parameter $n` — vérifier que chaque `$n` du tableau de paramètres correspond bien à une occurrence dans la requête. - **Multi-devises et TVA par localisation câblés dans la facturation** (17/08/2026, suite à l'échange « qu'en pensez-vous ? ») : en creusant `factures.js` pour écrire des tests financiers, découverte que la règle transverse « FCFA pivot, EUR à 655,957 fixe, autres devises verrouillées à l'émission, TVA selon localisation » n'était **pas implémentée** dans le code, alors que le **schéma la prévoyait déjà** — table `devises` (XOF/EUR à parité fixe, USD/GBP flottantes) et `taux_change` (historique), colonnes `factures.taux_applique/date_taux/taux_verrouille/montant_ttc_xof/libelle_principal`, `paiements.devise/taux_applique/montant_xof`, tout hérité du kit de démarrage dès le premier commit mais jamais câblé. Câblage fait dans `factures.js` :
  - `POST /api/factures` accepte `devise?` (défaut XOF) et `taux_applique?`. Pour une devise à parité fixe (`devises.flottante = FALSE`, ex. EUR), le taux vient de `devises.parite_xof` et **ignore** tout `taux_applique` fourni par l'appelant (parité non négociable). Pour une devise flottante (USD, GBP), soit l'appelant fournit `taux_applique` pour cette facture (archivé dans `taux_change`), soit le dernier taux connu pour cette devise est repris ; sans l'un ou l'autre, la création est **refusée** (`400`) plutôt que d'inventer un taux. Le taux retenu est figé sur la facture (`taux_verrouille=TRUE`) et sert à calculer `montant_ttc_xof` (contre-valeur FCFA, pour le reporting/pivot).
  - `taux_tva` par défaut : 18 % si `clients.pays` est Mali ou vide, 0 % sinon (prestation hors territorialité) — **valeur de départ, pas un avis fiscal**, toujours écrasée si `taux_tva` est fourni explicitement à la création ; à valider avec l'expert-comptable du cabinet avant de s'y fier telle quelle en production réelle.
  - `POST /api/factures/:id/paiements` : un paiement hérite automatiquement de la devise et du taux figés de sa facture (pas de règlement multi-devises sur une même facture — hors scope), et calcule `montant_xof`.
  - Frontend (`pages/facturation/`) : sélecteur de devise (XOF/EUR/USD/GBP), champ taux visible seulement pour les devises flottantes, champ TVA laissé vide par défaut pour appliquer la règle de localisation, affichage de la contre-valeur FCFA dans le tableau des factures.
  - **Tests** : `backend/tests/finance.test.js` (nouveau, 13 tests) — taux par qualité de rétrocession (30/25/10 %), règle « tout ou rien » (refus tant que la facture liée n'est pas intégralement encaissée, acceptation une fois soldée), TVA par défaut selon `clients.pays` et override explicite, XOF sans conversion, EUR à taux fixe avec tentative d'override ignorée, USD sans taux connu refusé, GBP avec taux fourni puis réutilisé sans le refournir, propagation devise/taux sur un paiement.   - Décisions actées avec l'utilisateur : **Administrateur IT** a les mêmes droits que l'Administrateur général sur toutes les actions métier (identité distincte pour la traçabilité, objectif « débloquer n'importe quelle situation ») ; **Avocat Of Counsel** identique à Avocat collaborateur (cohérent avec la règle de rétrocession qui les regroupe déjà à 25 %) ; **Assistant comptable** consultation/soumission uniquement, jamais décaissement/validation ; **Archiviste** pensé pour GED/courrier/bibliothèque mais pas verrouillé en dur (voir matrice ci-dessous).
  - **Système de permissions configurable** (remplace le câblage en dur `requireRole("associe","admin")` sur les actions métier) : nouvelle table `permissions_role` (role, action_code, autorise — clé composite, absence de ligne = refus par défaut, jamais d'accès implicite), catalogue statique des 44 actions configurables dans `backend/src/permissions.js` (même esprit que `MODELES` dans `actes.js`), middleware `requirePermission(actionCode)` qui a remplacé `requireRole` sur les **44 routes métier** (les 10 déjà réservées + les 34 jusque-là ouvertes à « tous rôles » — céder ce levier à un administrateur était la demande explicite de l'utilisateur, pas juste documenter l'existant). Seedé à la bascule pour reproduire exactement le comportement d'avant.
  - **Garde-fou anti-verrouillage** : le module Accès & permissions lui-même (comptes, rôles, délégations) N'EST PAS dans cette table — reste `requireRole("associe","admin_general","admin_it")` codé en dur, pour qu'une manipulation malheureuse dans la matrice ne puisse jamais retirer à tout le monde le moyen de la corriger.
  - **La matrice elle-même** (`GET/PUT /api/acces/permissions`, écran « Matrice des permissions » dans Accès & permissions) est **plus restreinte que le reste du module** : réservée à Associé + Administrateur IT uniquement (précision explicite de l'utilisateur — l'Administrateur général peut gérer les comptes mais pas modifier qui a le droit de faire quoi). Deux middlewares `requireRole` empilés (ET logique) : le garde commun du routeur laisse passer `admin_general`, le second le rejette spécifiquement sur ces deux routes.
  - `retrocessions.component.ts` : la suggestion auto de qualité par rôle du bénéficiaire mise à jour (`juriste` → 10 %, `of_counsel`/`stagiaire` → 25 % comme `collaborateur`) — sans ce correctif un juriste aurait été suggéré à 25 % au lieu de 10 %.
  - ⚠️ **Piège rencontré en migrant la production** : `ALTER TYPE ... ADD VALUE` suivi de son utilisation (dans `enum_range()`) au sein du **même fichier** importé via `gcloud sql import sql` échoue (`ERROR_RDBMS`), même en séparant les instructions par des points-virgules hors de toute transaction explicite dans le fichier — l'outil d'import Cloud SQL semble empaqueter tout le script importé dans une transaction unique côté serveur, contrairement à `psql -f` en autocommit. **Solution qui a fonctionné** : scinder en deux fichiers/imports Cloud SQL strictement séquentiels — (1) les `ALTER TYPE`, (2) la `CREATE TABLE` + le seed qui utilise les nouvelles valeurs — chaque `gcloud sql import sql` étant une opération/session distincte, la deuxième ne démarre qu'une fois la première pleinement `done`. À réappliquer si un futur changement de schéma ajoute une valeur d'enum réutilisée dans le même lot.
  - Vérifié en local (Docker, schéma neuf) et en production : comptes créés/validés pour `archiviste` et `admin_it`, bascule d'une permission en direct (désactivation de `clients.creer` pour `archiviste` → 403 immédiat, réactivation → 201 de nouveau), `admin_general` confirmé exclu de la matrice (403 sur GET et PUT) tout en gardant le reste du module Accès & permissions (200 sur `/audit`). Suite de tests (`regression.test.js` + `finance.test.js`, 21 tests, aucun ne référence le rôle `admin` littéral) toujours verte après la bascule.
  - Registre des commandes (artefact publié précédemment) mis à jour au même lien : 11 statuts, mention explicite que les valeurs affichées sont modifiables via la matrice et peuvent ne plus refléter l'état courant.
- **Gestion de la concurrence (chevauchement entre utilisateurs)** (17/08/2026, suite à une question directe de l'utilisateur) — état des lieux honnête d'abord : JURIA n'a **aucune collaboration temps réel** (pas de WebSocket, pas d'indicateur de présence). Le motif `COALESCE($n, colonne)` déjà utilisé partout protège nativement le cas « deux personnes modifient des **champs différents** de la même fiche en même temps » (chaque colonne non envoyée relit sa valeur courante en base au moment de l'exécution, pas une copie figée côté client) — mais pas le cas « même champ, même moment » (dernier arrivé écrase silencieusement). Deux correctifs appliqués :
  - **Garde contre le double déclenchement d'une transition d'état irréversible** : généralisée à **4 routes qui ne l'avaient pas** (trouvé en auditant les 10 actions de transition à la suite de la question) — `retrocessions.decaisser` (`AND statut <> 'decaissee'`), `taches.valider` (`AND statut <> 'termine'`), `conflicts.decision` (`AND decision = 'en_attente'`), `cabinet.conges.decision` (`AND statut = 'demande'`). Chacune renvoie désormais `409` avec un message explicite (« déjà décaissée/validée/traité(e) par quelqu'un d'autre entre-temps ? ») au lieu d'écraser silencieusement `decaisse_par`/`valide_par`/`decide_par`/`approuve_par`. Les 4 routes qui avaient déjà cette garde (`audiences.role.valider/diffuser`, `depenses.decision/decaisser`, `acces.valider`) n'ont pas été touchées. `cabinet.bulletins` volontairement laissé en upsert (`ON CONFLICT DO UPDATE`) — régénérer/corriger un bulletin du même mois est un usage légitime, pas un bug.
  - **Verrouillage optimiste sur `PUT /api/clients/:id`** (seule route d'édition multi-champs d'une fiche existante — `dossiers.js` n'a pas de PUT du tout) : body optionnel `maj_le_attendu` (valeur de `clients.maj_le` vue au chargement) ; si fourni et périmé, `409` avec message clair plutôt qu'un écrasement muet. ⚠️ Piège rencontré et corrigé : une comparaison stricte `maj_le = $17` échouait presque toujours, y compris pour une écriture légitime immédiatement après le chargement — `TIMESTAMPTZ` est stocké à la microseconde en Postgres, mais un aller-retour JSON/JS Date arrondit à la milliseconde ; la comparaison doit tronquer les deux côtés (`date_trunc('milliseconds', maj_le) = date_trunc('milliseconds', $17::timestamptz)`). Sans `maj_le_attendu` fourni, comportement historique inchangé (pas de vérification). Frontend (`client-detail.component.ts`) mis à jour pour l'envoyer et gérer le `409` en rechargeant automatiquement la fiche.
  - Numérotation automatique (référence courrier, numéro dossier/facture) : fenêtre de course théorique sur le calcul `COUNT(*)+1`, mais une contrainte `UNIQUE` en base empêche tout doublon réel — au pire la requête concurrente perdante échoue avec une erreur brute (pas encore rendue conviviale, noté mais non traité).
  - Volontairement non fait (jugé disproportionné pour la taille du cabinet sauf besoin exprimé) : présence en temps réel, verrouillage pessimiste explicite, rafraîchissement automatique des écrans collaboratifs (rôle d'audience, plan d'action kanban), historique de versions.
  - Vérifié en local (21/21 tests, + tests manuels ciblés sur chacune des 5 corrections : double décaissement, double validation, double décision de conflit, double décision de congé, verrou optimiste client avec les 3 cas — bonne valeur/valeur périmée/sans verrou) et en production (double validation de tâche confirmée : 200 puis 409).
- **Messagerie instantanée interne** (17/08/2026, module 18, hors des 17 initiaux) : demandée par l'utilisateur pour dialoguer entre deux ou plusieurs personnes (échanges dossier, instructions, informations diverses), référence donnée = le chat écrit de Zoom. Distincte de `communications.js` (journal de traçabilité d'un dossier, pas un canal de discussion).
  - **Choix d'architecture déterminant** : JURIA tourne sur Cloud Run (sans état, potentiellement plusieurs instances) — un vrai chat « instantané » demande normalement un composant de diffusion inter-instances (Redis/Firestore/Pub-Sub). Utilisé **Postgres LISTEN/NOTIFY** à la place : une notification émise par une instance est reçue par toutes les connexions en écoute, quelle que soit l'instance qui les détient — pas de service GCP supplémentaire, messages gardés dans la même base sauvegardée/auditée que le reste (pas de fragmentation des échanges professionnels dans un second datastore, point jugé important pour un cabinet d'avocats). Diffusion côté client via **Server-Sent Events** (`EventSource`, auto-reconnexion native du navigateur) plutôt qu'un WebSocket bidirectionnel — l'envoi reste un `POST` classique, seule la réception a besoin d'un canal poussé.
  - **Schéma** : `conversations` (titre optionnel, `dossier_id` optionnel), `conversation_participants` (PK composite, `dernier_lu_le` pour le calcul des non-lus), `messages`. 2 nouvelles entrées dans le catalogue de permissions (`messagerie.creer_conversation`, `messagerie.envoyer_message`), ouvertes à tous les 11 rôles par défaut.
  - **Backend** : `backend/src/messagerie-bus.js` (nouveau) — connexion PG dédiée `LISTEN` (hors du pool `db.js`, avec reconnexion auto sur coupure) + registre en mémoire des flux SSE ouverts localement ; `pousserLocalement()` n'écrit que sur les flux de CETTE instance, la diffusion inter-instances passe uniquement par `NOTIFY`/`pg_notify()`. `backend/src/routes/messagerie.js` (nouveau) : `GET/POST /conversations`, `GET/POST /conversations/:id/messages`, `POST /conversations/:id/lu`, `GET /non-lus`, `GET /stream` (SSE). `/stream` ne peut pas passer par le middleware `authenticate` standard (`EventSource` ne pose pas d'en-tête `Authorization`) — jeton accepté en query (`?token=`), vérifié à la main avec le même `SECRET`.
  - ⚠️ **Piège rencontré et corrigé** : la connexion `LISTEN` dédiée, démarrée au chargement du module, empêchait la suite de tests Jest de se terminer (process qui ne rend jamais la main, timeout au lieu d'un résultat) — corrigé en sautant `demarrerEcoute()` quand `NODE_ENV=test` (positionné automatiquement par Jest). Sans ce garde-fou, toute future suite de tests important ce module se bloquerait silencieusement.
  - **Frontend** : `core/messagerie.service.ts` (nouveau, `providedIn: 'root'`) — un seul `EventSource` partagé pour toute l'application (ouvert une fois après connexion dans `login.component.ts`, fermé à la déconnexion dans `app.component.ts`), pas une connexion par écran ; alimente à la fois la pastille de non-lus de la barre latérale et l'écran dédié. Pas d'ajout optimiste du message envoyé côté client : il revient via son propre écho SSE (l'auteur est lui-même abonné en tant que participant), évite un doublon. `pages/messagerie/messagerie.component.ts` (nouveau).
  - **Déploiement** : délai de requête Cloud Run du service `juria` porté à 3600s (`--timeout=3600`) pour que le flux SSE ne soit pas coupé toutes les 5 minutes (le navigateur reconnecterait de toute façon via `EventSource`, mais c'est plus fluide).
  - Vérifié en local (21/21 tests toujours verts après le correctif `NODE_ENV`, test SSE réel via `curl -N` confirmant la réception en quelques centaines de ms, compteurs de non-lus testés dans les deux sens) et **en production réelle** : message envoyé par un compte, reçu en direct via SSE par un second compte à travers deux requêtes HTTP distinctes (donc potentiellement deux instances Cloud Run différentes) — confirme que LISTEN/NOTIFY diffuse correctement au-delà d'une seule instance, pas seulement en local à instance unique.
